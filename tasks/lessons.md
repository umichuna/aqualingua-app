## 2026-08-28: 作業開始時に `git fetch` せず、2か月前のコードを診断してしまった

**何が起きたか**
「全体メンテナンス」の依頼で調査を始めた際、`git status` が
「Your branch is up to date with 'origin/master'」と表示したのを信じて作業した。
実際にはローカルが **33コミット・約2か月分**遅れており、
既に修正済みの問題を「未修正のバグ」として報告し、修正までしてしまった。
作成したPRも古いベースのため競合し、マージできなかった（オーナーには
「エラーも出ずにマージが失敗する」という形で見えていた）。

**なぜ起きたか**
`git status` の「up to date」は、**最後に fetch した時点の情報**との比較でしかない。
fetch していなければ、リモートがどれだけ進んでいても「最新」と表示される。
これを「GitHubと同期済み」の意味だと誤解した。

**次回どうすべきか**
- **調査・修正を始める前に必ず `git fetch --all --prune` を実行する。**
  `git status` の表示だけを根拠にしない。
- ブランチを切る前に `git log HEAD..origin/master --oneline | wc -l` で
  取り込めていないコミット数を確認する（0でなければ先に取り込む）。
- 未マージのPRが無いかも確認する（`gh pr list`）。
  古いPRに未反映の修正が溜まっていることがある。

## 2026-08-28: 「クラウドを守る条件」を推測で判定すると隙間ができる

**何が起きたか**
新端末が復元前に保存してクラウドを消す事故を防ぐため、
「未同期の新端末か（`userStatus.lastUpdated === 0`）」で判定していた。
しかしチュートリアルやクイズを1回でも行うと `lastUpdated` に時刻が入り、
保護の対象から外れる。結果「新端末で1回遊んでから保存」で
**警告もなくクラウドのデータが全部消える**隙間が残っていた。

**なぜ起きたか**
「空配列なら常にスキップ」にすると別の不具合（魚を全部ボックスに移した場合など）が
出るため、代わりに端末の状態から意図を**推測**する方式にした。
推測は必ず外れるケースが出る。

**次回どうすべきか**
- **データを消す操作の可否を、状態からの推測で決めない。本人に確認する。**
  既定は「消さない」にして、了承フラグ（例: `allowEmpty: true`）付きの
  再送でのみ実際に削除する。
- 「守る条件」を実装したら、**それをすり抜ける経路がないか具体的な操作手順で
  書き出して検証する**（今回は3ケース並べて初めて隙間が見えた）。

## 2026-08-27: DB接続不可 → 真因はパスワードではなくデータベース内ユーザー登録の消失

**何が起きたか**
コードにパスワードが書かれていることに気づいたオーナーが Azure Portal で
パスワードを変更したところ、アプリがAzure SQLに接続できなくなった。

**なぜ起きたか**
`Login failed for user 'xxx'` は通常パスワード不一致を疑わせるが、実際は
**対象データベース内のユーザー登録（`sys.database_principals`）が存在しなかった**。
サーバーレベルのログインは有効でも、DB個別のユーザーマッピングが無いと同じエラーになる。

**次回どうすべきか**
- 「Login failed」が出たら、パスワードだけでなく
  `SELECT * FROM sys.database_principals WHERE name='<user>'` で
  **ユーザー登録の有無も必ず確認する**。
- `node setup-db-user.js ensure` で両方をまとめて確認・修復できる
  （`az login` 済みが前提。Azure AD認証なのでパスワードをファイルに書かない）。
- 本番DBへの操作は、実行前に必ずオーナーへ内容を1行で確認してから行う。

## 2026-08-27: 公開リポジトリに認証情報を平文で置いていた

**何が起きたか**
セットアップ用スクリプトにAzureの認証情報とDBパスワードが平文で書かれたまま、
**公開設定のGitHubリポジトリ**にコミットされていた（2026-06-23〜08-01）。

**なぜ起きたか**
`.gitignore` は `.env*` を除外していたが、**スクリプト内のベタ書きはその網に掛からない**。
使い捨てのつもりのスクリプトだったため、そのままコミットしてしまった。

**次回どうすべきか**
- 認証情報は `.env.local`（Git管理外）か Azure AD認証（`DefaultAzureCredential`）で扱う。
  使い捨てスクリプトでも例外にしない。
- コミット前に走査する:
  `git ls-files -z | xargs -0 grep -lniE "password|secret|AIzaSy|GOCSPX-"`
- リポジトリの公開設定を確認する（`gh repo view --json visibility`）。
- **一度公開した認証情報はファイルを消してもGit履歴に残る。
  唯一の確実な対処はパスワード自体の変更（ローテーション）。**

## 2026-08-27: `npm run build` の直後に `npm run dev` するとAPIが404になる

**何が起きたか**
動作確認で本番ビルドを実行した直後に開発サーバーを起動したところ、
トップページは200なのに `/api/*` が**すべて404**を返し、「APIが壊れた」と誤認しかけた。

**なぜ起きたか**
本番ビルドと開発サーバーが同じ `.next` フォルダを共用しており、
本番用の生成物が残った状態で開発サーバーを起動するとルート解決に失敗することがある。

**次回どうすべきか**
- `npm run build` の後に `npm run dev` で確認するときは、先に `rm -rf .next` する
  （ビルド生成物のみでソースには影響しない）。
- 「APIだけ404」が出たらコードを疑う前に `.next` の削除を試す。
  Service Worker 由来のキャッシュ問題とは切り分けること。
