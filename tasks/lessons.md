# 教訓ログ

## 2026-08-26: DB接続不可 → 真因はパスワードではなくデータベース内ユーザー登録の消失

**何が起きたか**
オーナーがコードにパスワードが書かれていることに気づきAzure Portalでパスワードを変更したところ、
アプリがAzure SQLに接続できなくなった。

**なぜ起きたか**
「Login failed for user 'aqualingua_user'」というエラーは通常パスワード不一致を疑わせるが、
実際に調べると原因は2段階だった。
1. パスワード変更自体は正しく行われていたが、`.env.local`側が古いままだった（表面上の原因）
2. パスワードを合わせても同じエラーが再現 → 調査の結果、**対象データベース
   (`free-sql-db-2279904`)内にaqualingua_userのユーザー登録(`sys.database_principals`)が
   存在しなかった**（サーバーレベルのログインはあるのに、DB個別のユーザーマッピングがない状態）。
   Azure SQLでは、ログインは有効でもDB内ユーザーがないと同じ「Login failed」エラーになるため、
   パスワードの問題と区別がつきにくい。

**次回どうすべきか**
- 「Login failed」エラーが出た時は、パスワード不一致だけでなく
  `SELECT * FROM sys.database_principals WHERE name='<user>'`（対象データベースに接続して確認）
  でユーザー登録自体の有無も必ず確認する。
- Azure ADのDefaultAzureCredential（`az login`済みのCLIを利用）で管理者接続すれば、
  漏洩済みの管理者パスワードを使わずに安全にログイン/ユーザーの調査・再作成ができる。
- パスワード変更やユーザー再作成など本番DBへの操作は、実行前に必ずオーナーへ内容を
  1行で確認してから実施する。

## 2026-08-27: 公開GitHubリポジトリにAzureアカウントのパスワードが平文で置かれていた

**何が起きたか**
システムメンテナンスで全体調査したところ、`aqualingua-app` リポジトリが GitHub 上で
**PUBLIC（誰でも閲覧可能）** であり、そこに以下が平文で含まれていた。
- Azureアカウント `chandoichi@sukonokuni.onmicrosoft.com` のパスワード（サブスクリプション権限あり）
- Azure SQL のアプリ用パスワード（旧）
対象ファイル: `create-db-user.js` / `setup_azure_user.js` / `setup_azure_sql.py` /
`create-db-user-aad.js`。2026-06-23 のコミット `2a06c70` で追加され、約2か月間公開されていた。

**なぜ起きたか**
DBセットアップを急ぐ中で、使い捨てのつもりの補助スクリプトに認証情報を直接書き込み、
そのままコミットした。`.gitignore` は `.env*` を除外していたが、**スクリプト内の
ベタ書きはその網に掛からない**。

**次回どうすべきか**
- 認証情報は必ず `.env.local`（Git管理外）か Azure AD 認証（`DefaultAzureCredential`）で扱い、
  スクリプトに直接書かない。使い捨てスクリプトでも例外にしない。
- 新規リポジトリを作るときは公開/非公開を必ず確認する（`gh repo view --json visibility`）。
- コミット前に `git ls-files -z | xargs -0 grep -lniE "password|secret|AIzaSy|GOCSPX-"` で走査する。
- **一度公開された認証情報は、ファイルを消してもGit履歴に残る。唯一の確実な対処は
  パスワード自体を変更（ローテーション）すること。**
- 恒久対応として、AAD認証のみを使う `setup-db-user.js` に統合し、旧スクリプトは削除した。

## 2026-08-27: `npm run build` の直後に `npm run dev` するとAPIが404になる

**何が起きたか**
動作確認で `npm run build`（本番ビルド）を実行した直後に `npm run dev` を起動したところ、
トップページは200で表示されるのに `/api/auth/session` や `/api/sync/pull` が**すべて404**を返した。
一瞬「APIが壊れた」と誤認しかけた。

**なぜ起きたか**
本番ビルドと開発サーバーが同じ `.next` フォルダを共用しており、本番用の生成物が残った状態で
開発サーバーが起動するとルート解決に失敗することがある。コードの不具合ではない。

**次回どうすべきか**
- `npm run build` の後に `npm run dev` で確認するときは、先に `.next` を削除する
  （`rm -rf .next`。ビルド生成物のみでソースには影響しない）。
- 開発中に「APIだけ404」「ルートが見つからない」症状が出たら、コードを疑う前に
  まず `.next` の削除を試す。Service Worker 由来の症状とは切り分けること。
